# 簡體轉繁體 轉換規則

## 觸發方式

使用者輸入 `轉換 <指定目錄>` 即啟動本規則，對該目錄進行掃描與轉換。
未指定目錄時不執行（不預設全域掃描）。

---

## 本文件與產出位置

| 項目 | 本專案位置 |
| --- | --- |
| 規則本體（本檔） | `rule/conversion-rules.md` |
| 執行報告 | `rule/reports/`（首次執行時自動建立） |
| 工作暫存檔 | `rule/` 底下，檔名以 `_` 前綴 |
| 討論紀錄 | `rule/chat.md`（規則演進的討論留在這裡） |

> 這是模板預設。實際專案若採 `dev-notes/` 慣例，整組換成 `dev-notes/` 即可，
> 規則內容不受影響——以下各節提到「報告目錄」「暫存檔」「討論紀錄」時，指的都是上表的位置。

## 一、轉換範圍

掃描目標包含以下三個層級:

1. **檔案內容** — 文件內出現的簡體字
2. **檔案名稱** — 檔名含簡體字須一併改名
3. **目錄名稱** — 目錄含簡體字須一併改名

副檔名不限（`.md`、`.ts`、`.js`、`.html`、`.css`、`.json`、`.txt` 等）。
`.zip` 等壓縮檔內不掃描（需先解壓）。

### 排除目錄（不掃描內容、不改動）

以下目錄預設排除，掃描時直接跳過（含其內所有子項目）:

**依賴/建置產物**
- `node_modules/`
- `dist/`
- `.next/`
- `.cache/`
- `bower_components/`
- `jscoverage_lib/`

**版控/IDE/OS 元資料**
- `.git/`、`.svn/`、`.hg/`、`.CVS/`
- `.idea/`、`.vscode/`、`.settings/`
- `.DS_Store`、`thumbs.db`、`._*`

**⚠️ `build/` 特例**
- **不列入預設排除**。原因: 教材／範例專案裡的 `build/` 有可能是教學示範原始碼而非建置輸出
  （實例：某課程專案 `08.工程化/*/proj/build/` 是示範 TS 模組解析用的原始碼）。
- 實際執行時，若遇到 `build/` 目錄，列入「待覆核項目」由使用者判斷是否轉換。

### 排除檔案類型（不轉內容，但檔名仍掃描）

以下副檔名**不轉換檔案內容**（二進位或自動產生），但**檔名若含簡體字仍需改名**:

**二進位/媒體**
- `.xmind`、`.pptx`、`.key`、`.pdf`
- `.png`、`.jpg`、`.jpeg`、`.gif`、`.svg`、`.ico`
- `.zip`、`.tar`、`.gz`

**自動產生檔**
- `package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`

### 特殊檔案處理

- **`package.json`** — 掃描並轉換（`description`、`scripts` 等欄位內簡體轉繁），package.json 內容是給人看的，轉換無副作用
- **`assets/` / `public/` 目錄下的圖片** — 檔名若含簡體要改名時，**必須同步更新引用該圖片的所有 `.md`/`.html`/`.vue` 等檔案內的路徑**

### 教學語料與其衍生資料（不轉，且須同進退）

當某個資料檔是**程式的輸入或輸出**、而非給人閱讀的說明文字時，轉繁會改變程式的執行結果，破壞教材示範。這類檔案**保留簡體不轉**，並列入報告的「刻意保留」項。

判斷準則：

1. **教學語料**——被課件程式讀入做處理的原始資料。轉繁會改變處理結果。
   - 例：`07. 詞元/corpus.txt`（被 `課件.ipynb` 讀入做 BPE 分詞示範，轉繁會改變 token 切分結果）
2. **衍生資料**——由該語料經程式產生的檔案。**必須與來源檔同進退**，否則兩者對不上。
   - 例：`07. 詞元/bpe_vocab.json`（`bpe_train(corpus)` 的產物）。corpus 既保留簡體，詞表也必須保留

> **易漏點**：衍生資料檔常是 `.json`、`.txt` 等一般文字副檔名，掃描時會被當成正常待轉檔案。**決定某個語料保留不轉時，必須一併追查它的產物**——搜尋課件中讀寫該語料的程式碼，找出輸出檔一併排除。

## 二、字形轉換

### 轉換方式

採 **字元層級** 簡轉繁，使用台灣字形變體，**不做用語替換**。

- **採用 OpenCC `s2tw`** 設定檔：套用台灣字形變體
  - 範例：`爲` → `為`、`衆` → `眾`、`什麽` → `什麼`
- **不使用 `s2twp`**，因為 `s2twp` 會做詞彙替換（如 `軟件` → `軟體`）

### 後置字元替換表（補 OpenCC 未處理的台灣變體）

OpenCC `s2tw` 沒有覆蓋到的字元變體，以下表做**一對一字元替換**：

| 原字 | 替換為 | 常見詞例／理由 |
| --- | --- | --- |
| 賬 | 帳 | 賬號→帳號、賬戶→帳戶、賬單→帳單 |
| 檯 | 台 | 控制檯→控制台、櫃檯→櫃台 |
| 瞭 | 了 | 還原 OpenCC 的短語級替換（例：`為了解決` 被誤判為含 `了解`→`瞭解`）。簡體原文不使用 `瞭`，一律還原為 `了` 以符「一字對一字」 |

> 未列入此表的字元（例如 `軟`、`件`、`網`、`絡` 等），即使台灣有其他寫法，**一律保留 OpenCC 輸出不再替換**。

### 詞級修正表（修復來源端的「過度轉換」錯字）

部分教材的來源檔內文，**在交付前就已被作者用劣質工具做過一次簡轉繁**，過程中把某個簡體字錯配成「字形正確但用字錯誤」的繁體字。這類字本身是合法繁體，OpenCC `s2tw`（單向簡→繁）對它**無字可轉、原樣放行**，因此後置字元替換表也救不回。

典型案例：簡體 `系统` 被誤轉成 `係統`（應為 `系統`）。`系` 在簡轉繁時對應 `系/係/繫`，來源工具選錯成 `係`。但 `係` 在 `關係`、`係數` 中是正確的，**不可做字元級 `係→系`**，必須走**詞級**一對一替換：

| 錯誤詞 | 修正為 | 理由／辨識 |
| --- | --- | --- |
| 係統 | 系統 | 系统→系統（操作係統、響應式係統、生態係統…） |
| 係列 | 系列 | 系列→系列（一係列） |
| 聯係 | 聯繫 | 简体 `联系`→繁體應作 `聯繫`，被誤配成 `聯係` |

> **保留不動的正確詞**（同含 `係` 但用字正確）：`係數`（溫度係數）、`關係`、`關係到`。
>
> 套用方式：以**完整詞**為單位比對替換，不得拆成單字 `係→系`。日後若再發現同類來源端過度轉換錯字（如 `面/麵`、`制/製`、`复/複/復` 等選錯字），於本表續列，並在討論紀錄中記錄。

### 詞組切分漏轉表（修復 OpenCC 的「該轉未轉」）

與上表相反的另一類問題：OpenCC 以詞組為單位比對時，若某段文字**恰好命中另一個更長的詞條**，會依該詞條規則處理，導致其中的字被判定為「無需轉換」而原樣放行。

典型案例：`系统提示词采用 Markdown` 中的 `词采` 命中詞條 `詞采`（文采之意），OpenCC 因此把 `采` 當成該詞的一部分保留，未套用 `采用→採用`。這類漏字**第一輪掃描不會標記**，只有在**第二輪 dry-run** 才會浮現（切分邊界改變後才被正確識別）。

| 漏轉詞 | 修正為 | 辨識方式 |
| --- | --- | --- |
| 詞采用 | 詞採用 | `采用` 前接 `詞/词` 時被誤併為 `詞采`；一般語境的 `采用` OpenCC 可正確轉為 `採用` |

> **偵測方式**：轉換完成後務必跑第二輪 OpenCC dry-run。第二輪若出現差異，需逐一判讀屬於下列何者：
> 1. **變體切換**（`干↔幹`、`合↔閤`、`托↔託`、`制↔製`、`面↔麵`）→ 保留第一輪輸出
> 2. **後置替換表的正確結果**（`控制檯→控制台` 被第二輪要求改回 `控制檯`）→ 保留第一輪輸出
> 3. **OpenCC 誤判**（如 `太陽系→太陽繫`）→ 保留第一輪輸出
> 4. **真實漏轉**（如本表的 `采`）→ **必須修正**，並於本表續列
>
> 只有第 4 類要動；前三類一律保留。判讀時以「該字在此語境的正確繁體用字」為準，不可一律照第二輪輸出套用。

### 不替換用語的原則

保留原作者的用詞習慣；下列詞彙**維持原樣**（僅做字形轉換、不替換為台灣慣用詞）：

| 原文（簡體） | 轉換後（繁體） | 不改為 |
| --- | --- | --- |
| 软件 | 軟件 | 軟體 |
| 视频 | 視頻 | 視訊 |
| 网络 | 網絡 | 網路 |
| 服务器 | 服務器 | 伺服器 |
| 数据 | 數據 | 資料 |
| 程序 | 程序 | 程式 |
| 变量 | 變量 | 變數 |
| 对象 | 對象 | 物件 |
| 文件夹 | 文件夾 | 資料夾 |
| 默认 | 默認 | 預設 |
| 设置 | 設置 | 設定 |
| 缓存 | 緩存 | 快取 |
| 打印 | 打印 | 列印 |
| 鼠标 | 鼠標 | 滑鼠 |

> 原則：**一字對一字**（含台灣變體）。不做地區用詞替換、不做語意改寫、不調整語序。

## 三、CJK 標點前的多餘空白清除

當 **非空白字元** 與 **全形標點** 之間插入了空白（半形空格、全形空格、Tab），一律刪除該空白，使標點緊貼前字。

### 適用標點

`、`、`。`、`！`、`，`、`：`、`；`、`？`、`）`、`」`、`』`、`】`、`》`

### 範例

| 轉換前 | 轉換後 |
| --- | --- |
| 需要包管理器 ？ | 需要包管理器？ |
| 註冊地址 ，以便發佈 | 註冊地址，以便發佈 |
| 什麼是 workspace ？ | 什麼是 workspace？ |

### 適用範圍

- **僅套用在 `.md` 檔案的自然語言段落**
- **程式碼區塊（``` … ```）與行內程式碼（`…`）內不套用**
- 其他副檔名（`.vue` / `.ts` / `.js` / …）不套用，避免誤動格式化字串

### 實作（正規表示式）

```
pattern: (?<=\S)[ \t　]+(?=[、。！，：；？）」』】》])
replace: ""
```

> `　` 為全形空格。只刪除非換行空白，行首縮排（換行後的空白）不受影響。

## 四、引號規則

### 基本規則

成對引號（半形 `""` / `''`、全形 `“”`）一律轉為繁體中文全形括號:

- 外層 → `「」`
- 內層（巢狀）→ `『』`

### 範例

| 原文 | 轉換後 |
|---|---|
| `"你好"` | `「你好」` |
| `'再見'` | `「再見」` |
| `"他說'你好'"` | `「他說『你好』」` |
| `'外層"內層"外層'` | `「外層『內層』外層」` |
| `“資料結構”` | `「資料結構」` |
| 點選"確認"按鈕 | 點選「確認」按鈕 |

### 不可轉換的例外

以下情境中的 `"` / `'` **不得**轉換：

1. **程式碼字串界定符**：`const msg = "hello"` → 引號保留（字串內中文仍轉字形）
2. **JSON / YAML / TOML 鍵值**：`"name": "..."` → 保留
3. **HTML / XML 屬性**：`class="foo"` → 保留
4. **命令列參數**：`--flag="value"` → 保留
5. **正規表達式、路徑字面值**
6. **Markdown 程式碼區塊**（``` … ``` 或 `…` 內）
7. **英文語境**的直接引用（例如 `"Hello World"` 作為英文短語）
8. **非成對的單引號**（英文縮寫 `don't`、所有格 `Tom's`）保留原樣

> 判斷原則：若引號位於**自然語言的中文段落**中（引號內含中文或緊鄰中文字），才轉換；若位於**程式語法**中、或英文語境，一律保留。

## 五、程式碼區塊處理

### 轉換對象（會轉字形）
- Markdown 程式碼區塊（``` ``` ```）內的**註解**若含簡體 → 轉
- Inline code（`` ` ` ``）內的簡體 → 轉
- 各語言**註解**（`//`、`/* */`、`<!-- -->`、`#`、`"""..."""`）內簡體 → 轉
- **字串字面值**內的簡體（`const msg = "你好"`）→ 轉（字串是給使用者看的內容）

### 不轉換對象（保持原樣）
- 變數名、函式名、類別名、屬性 key（即使以拼音或中文命名）
- 程式語法關鍵字
- URL、檔案路徑、import 路徑
- **套件名稱、npm 套件 ID、module 名稱**
- **非給人閱讀的字串字面值** — API 參數、資料庫欄位名、協定關鍵字。
  上面「字串字面值要轉」的前提是那串字會被人看到；一旦字串本身是識別用途，轉了就改變程式行為
- 引號界定符本身（`"`、`'`、`` ` ``）
- 標點空白清除規則與引號規則**不**在程式碼區塊／行內程式碼中套用

## 六、檔名/目錄名改動流程

由於 Windows 對檔名大小寫不敏感、且改名影響 git 歷史，採兩階段流程:

### 階段 1 — 產生擬改名清單

掃描後列出對照表，等待使用者確認:

```
[目錄]
  course/<課程>/数据结构        →  course/<課程>/數據結構
  course/<課程>/子目錄/文档     →  course/<課程>/子目錄/文檔

[檔案]
  xxx/简体檔名.md               →  xxx/簡體檔名.md
```

### 階段 2 — 使用者確認後執行

**執行順序：先改檔案內容 → 再重新命名檔案 → 最後重新命名目錄（由深層往淺層）**，避免父目錄已改名導致子項路徑失效。

- 若目錄已納入 git 控管，優先使用 `git mv` 以保留歷史
- 若目錄為 untracked（git status 為 `??`），使用一般 `mv` 即可
- 若使用者駁回某項，可單獨排除後再執行

## 七、執行流程

每次轉換依以下順序執行：

1. **掃描**：找出所有含簡體字元或成對 `""` 的檔案 / 目錄 / 檔名
2. **分類**：依例外規則判斷哪些需轉換、哪些保留
3. **預覽**：列出將要變更的清單（路徑、改名對照、引號替換統計）給使用者確認
4. **執行**：取得同意後依序套用
   - 先改檔案內容
   - 再重新命名檔案
   - 最後重新命名目錄（由深層往淺層）
5. **驗證**：再次掃描確認無漏網之魚
6. **報告**：產出執行報告（見第八節）
7. **清理**：使用者確認驗收後刪除暫存檔（見第九節）

### 計畫與報告規範

- **擬定轉換計畫時不要附帶 git commit 建議**（不列分批 commit 節奏、不建議 commit 訊息）
- 分階段執行時，每一階段結束都要主動回報進度
- 計畫只聚焦於「要改什麼、怎麼改、順序」，版本控管由使用者自行決定

## 八、執行報告

### 儲存位置
報告目錄（見開頭「本文件與產出位置」，本模板為 `rule/reports/`，首次執行時自動建立）

### 檔名格式
`YYYY-MM-DD-HHmm-<指定目錄代稱>.md`

範例: `2026-04-22-1530-typescript-main.md`

### 報告內容
1. **執行摘要** — 指定目錄、掃描檔案數、異動檔案數
2. **內容異動清單** — 每個檔案轉換的字數/處數
3. **改名清單** — 已執行的檔名/目錄名對照
4. **字元/引號統計** — 簡→繁字數、引號替換次數
5. **跳過項目** — 被排除或無法處理的檔案（附原因）
6. **待覆核項目** — 不確定是否該轉的邊界案例
7. **剩餘未處理項目** — 若為分階段執行

## 九、工作暫存檔清理（強制）

執行過程中產生的腳本 / 中繼資料（例如掃描腳本、改名計畫檔、JSON 結果檔、dry-run 輸出、log 檔）視為**工作暫存**，非長期保留資產:

### 命名與位置

- 檔名前綴以 `_` 標記（如 `_convert_s2tw.py`、`_rename_plan.txt`、`_dry-run-output.txt`、`_run-output.txt`）
- 置於規則檔同層（見開頭「本文件與產出位置」）

### 清理時機（強制執行）

**任務結束（使用者確認驗收無誤）後，必須刪除所有為此次轉換產生的暫存檔。**

執行流程的最後一步：

1. 執行改名
2. 轉換內容
3. 產出報告
4. 使用者確認驗收無誤
5. **刪除所有 `_` 前綴的工作暫存檔**（含腳本、計畫檔、log 檔、dry-run 輸出等）

### 保留項目

- 報告目錄下的報告檔（長期保留，作為歷史紀錄）
- 規則本體（本檔）
- 討論紀錄檔

### 不可遺漏

- 即使腳本可重複利用，仍視為單次任務的暫存品
- 若日後需要再次轉換，重新產生即可（不留長期執行檔）
- 不得以「下次可能還會用」為由保留

---

## 十、邊界案例處理原則

遇到以下情形，**不自動處理，列入報告「待覆核項目」**:

- 疑似引用他人簡體原文（整段段落）
- 檔案為二進位或未知編碼
- 檔案已包含繁簡混雜（可能原作者刻意保留）
- 改名後會與既存檔案衝突
- OpenCC 第二輪 dry-run 仍有變更但非真實簡體字（變體切換，如 `合↔閤`、`托↔託`、`制↔製`、`面↔麵`、`干↔幹`）——保留第一輪輸出。第二輪差異的四類判讀見第二節「詞組切分漏轉表」
- **原文引號本身未成對**（如只有前引號 `“` 而缺收尾 `”`，或同一行半形 `"` 為奇數個）——引號規則整行跳過不套用，列入待覆核由使用者判斷是否補齊
- **自然語言段落中的 HTML 屬性／CLI 參數／JSON 鍵值**（如 `<img src="…" alt="…">`、表格內的 `end=""`）——引號一律保留，不因所在段落是中文而轉換

## 十一、風險與安全

- 涉及檔名或目錄重新命名時，若處於 git 控管下，優先使用 `git mv` 以保留歷史
- 每次執行僅處理使用者明確指定的範圍，不主動擴大
- 不可直接覆蓋已存在檔案；遇衝突列入待覆核項目
